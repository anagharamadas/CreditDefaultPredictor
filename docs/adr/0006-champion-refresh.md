# ADR-0006: How a running service learns that the champion alias moved

Status: ACCEPTED
Date: 2026-10-04
Phase: P11
Supersedes: none
Superseded by: none

ADRs are immutable once accepted. To change a decision, write a new ADR that supersedes
this one; do not edit this file.

---

## Context

P7 established that promotion and rollback are **alias moves**: serving loads
`models:/credit-default-granting@champion` and is never redeployed to change models.
That is the right shape, and P7 demonstrated both directions against the registry.

The P9 end-to-end walkthrough (#53) then found that the demonstration was incomplete.
The service resolves the alias once, in its startup lifespan, and never looks again:

```
registry:  @champion -> v3
GET /ready: {"model_version": 1}      <-- stale
POST /score: scored by v1, and the row STORED as version 1
docker compose restart api
GET /ready: {"model_version": 3}      <-- only now
```

Two distinct problems, and the second is the worse one:

1. **Rollback is P11's emergency path** — the operation that must be fastest and
   least error-prone. If it requires "move the alias *and* restart every replica",
   then the alias move is not a rollback; it is a note to self.
2. **The audit trail can contradict the registry.** During the stale window,
   decisions are recorded under a `model_version` the registry has already retired.
   The walkthrough produced two rows with identical inputs and identical scores filed
   under two different versions. The prediction store exists to make decisions
   explicable after the fact; a version field that can be wrong defeats it.

A third problem was latent in the fix rather than in the bug. The model, its name and
its version were three separate attributes on application state. Any mechanism that
swaps them is a chance to score with one model and record another — so the fix had to
address coherence, not just freshness.

## Decision

**Poll the alias on a timer and hot-swap, with a bounded staleness window that
`/ready` publishes.**

- A **cheap probe** (`resolve(alias)`) asks only which version the alias points at —
  one small registry call, no artifact download. It runs every
  `MODEL_REFRESH_SECONDS` (default **30**).
- A **full load** happens only when that answer changes.
- The swap is a single assignment of a **frozen `ServingModel(model, name, version,
  loaded_at)`**. Requests read it once into a local, so each request completes against
  one consistent triple. A swap arriving mid-request cannot split it.
- A **probe failure is not fatal.** The loaded model keeps serving, and the error
  surfaces on `/ready` as `alias_check_error`. A registry outage should not take down
  a service that already holds the model it needs.
- `/ready` reports `model_alias`, `model_version`, `model_loaded_at`,
  `alias_checked_at`, `staleness_budget_seconds` and `alias_check_error`.
- `MODEL_REFRESH_SECONDS=0` disables polling, pinning a replica to the version it
  started with — useful when reproducing a past decision. `/ready` then reports a null
  budget, so the pinning is visible rather than silent.

**The honest statement of what this buys:** rollback is not instantaneous. It is late
by at most 30 seconds per replica, with no restart and no coordination, and the
lateness is measurable from outside the process.

## Alternatives considered and rejected

**Re-resolve the alias on every request — rejected.** Always correct, and tempting for
that reason. But it puts a registry round trip inside the scoring path, which couples
p99 latency to MLflow and makes a registry outage an outage of a service that does not
otherwise need the registry. At the measured ~32 ms per request, this is a large
relative cost for freshness nobody asked to be perfect.

**An explicit `/reload` endpoint called by the promotion step — rejected, and this is
the interesting one.** It is cheaper than polling and gives immediate effect. It fails
on coupling: the promoter must then know every running replica and reach it. That is
precisely the knowledge the alias indirection exists to remove — it turns a registry
operation back into a deployment operation, and it degrades silently as replicas
scale, because a replica nobody told stays wrong indefinitely with nothing to show for
it. Polling has the opposite failure mode: every replica converges on its own, and the
worst case is a known, bounded delay.

**Restart as the documented mechanism — rejected, though defensible.** For a
single-replica local stack this is simple and arguably honest. Rejected because the
restart window is exactly when a rollback is most urgent, and because the stale
`model_version` in the audit trail is a correctness problem that documentation does
not fix.

**A registry webhook — not available.** MLflow's model registry webhooks are not part
of the self-hosted server pinned by ADR-0001. Reconsider if that changes: push would
beat poll on both latency and cost.

## Consequences

Positive:
- Rollback is a one-line alias move again, with no restart, for any number of
  replicas.
- The recorded `model_version` cannot disagree with the model that produced the score.
- Staleness is a published number rather than an assumption.

Negative / accepted with eyes open:
- **A rollback can be up to 30 seconds late.** Accepted and stated; the runbook quotes
  the budget rather than claiming immediacy.
- **A background task per process.** It sleeps almost all the time and does one small
  registry call per interval, but it is a moving part that did not exist before.
- **A bad promotion propagates automatically too.** The quality gate (P9) is the
  control for that, and it is upstream of the alias move by design.
- **Two replicas can briefly serve different versions** mid-swap. Visible in the store
  via `model_version`, bounded by the same 30 seconds, and preferable to the
  alternative of all replicas being confidently stale.

## Review

Revisit if MLflow gains usable registry webhooks (push beats poll), if replica counts
grow enough that per-replica polling becomes a measurable load on the tracking server,
or if a future requirement needs rollback faster than the poll interval — in which
case `/reload` returns as a *supplement* to polling, not a replacement for it.
