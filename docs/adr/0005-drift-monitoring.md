# ADR-0005: Drift monitoring — implement a narrow metric set, no monitoring library

Status: ACCEPTED
Date: 2026-09-09
Phase: P10
Supersedes: none (closes the slot left OPEN in ADR-0001)
Superseded by: none

ADRs are immutable once accepted. To change a decision, write a new ADR that supersedes
this one; do not edit this file.

---

## Context

ADR-0001 locked six tools and left drift monitoring open until P10, when the
requirement would be concrete. It now is, and it has an unusual shape:

- The drift here is **real and already measured three times** — the class-balance
  trend (P2), the calibration assessment (#39: mean predicted 0.157 vs observed
  0.184, ECE growing 0.027 → 0.064 into later vintages), and the slice report
  (#41: month-by-month gaps widening −5.5pp → −7.2pp). We are not searching for
  drift. We know what it is and roughly how large.
- EVAL_PROTOCOL requires **alert thresholds justified in writing, not copied from a
  default**.
- Labels arrive months to years late, so the hard part (#57) is measuring performance
  when the answer is not yet known — not computing distribution distances.

## Decision

**Implement the metric set directly — PSI and KS for feature drift, the same two for
prediction drift — with thresholds chosen and justified in this repository. No
monitoring library is added.**

Scope is deliberately narrow: two well-understood statistics, applied per feature per
replay month, plus prediction-distribution drift and the label-lag performance work
that no library does for us anyway. Each implementation is tested against cases with
known answers (identical distributions → zero; a shifted distribution → a value
computed by hand).

## Alternatives considered and rejected

**NannyML — rejected on evidence, not preference.** Its distinctive capability is
exactly our hard problem: estimating performance before labels arrive (CBPE). But
CBPE works by treating the model's predicted probabilities as estimates of its own
correctness, which requires those probabilities to be well calibrated. We have
*measured* that ours are not, and that the miscalibration **grows with the drift we
would be using it to detect** (#39). Applying it here means applying a method whose
central assumption we have already falsified, on precisely the data where it fails
worst — and it would fail quietly, producing plausible numbers. If the calibration
finding were reversed, this decision should be revisited first.

**Evidently — rejected for this project, not in general.** It would produce reports
quickly and is the conventional choice. Three reasons against it here: its main value
is a large set of metrics *with defaults*, and the protocol specifically forbids
unjustified default thresholds; it has had breaking changes across major versions
(RISK_REGISTER R9), which is a poor trade for ~50 lines of statistics; and ADR-0001
already accepted "depth over breadth" as this project's posture, having judged that
each half-learned tool is an interview liability rather than an asset.

We are not claiming Evidently is the wrong tool generally. For a team running many
models it is very likely right — you do not want every team writing its own PSI. That
is not this project.

**Grafana/Prometheus for the dashboard — deferred, not rejected.** Operational
metrics plumbing is a different question from drift statistics; #58 decides how the
results are displayed and may still reach for something off the shelf.

## Consequences

Positive:
- Every number on the dashboard has a definition we wrote and can defend, and every
  threshold has a stated reason — which is the actual requirement.
- No new dependency, no version churn, nothing to re-learn after an upgrade.
- The implementation is small enough to be read in full during an interview.

Negative / accepted with eyes open:
- **No "used Evidently" line on the CV.** Accepted: being able to explain what PSI
  measures, where it misleads, and why we chose the threshold is the stronger
  position, and it is the one this project is built to demonstrate.
- **We own the correctness.** A subtle statistical error is now ours to make.
  Mitigated by testing each metric against hand-computed cases and by keeping the set
  small enough to verify.
- **Less breadth of metric.** We will not get, for free, the dozen additional tests a
  library would offer. Accepted: metrics nobody can justify are not monitoring.

## Review

Revisit if the calibration finding reverses (which would re-open NannyML), if the
metric set needs to grow beyond what we can justify individually, or if this moves
from one model to several — the argument for a shared library strengthens with every
additional model.
