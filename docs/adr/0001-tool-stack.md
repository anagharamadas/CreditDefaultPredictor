# ADR-0001: Tool stack for the MLOps pipeline

Status: ACCEPTED
Date: 2026-08-18
Phase: P0
Supersedes: none
Superseded by: none

ADRs are immutable once accepted. To change a decision, write a new ADR that supersedes
this one; do not edit this file.

---

## Context

Solo portfolio project, junior operator (1-2 years), local-first, USD 20 total budget,
64 GB RAM, ~343 hours over 60 days. The evaluated signal is operational maturity, not
model accuracy. The dataset (1.6 GB raw) fits in memory with an order of magnitude to
spare, so no tool is chosen for scale; tools are chosen for what they demonstrate and for
how defensible each is under interview questioning.

A stack fork was surfaced in P0 across seven slots. This ADR records the decision on six of
them. Two slots remain open by design (drift monitoring, deploy target) and will get their
own ADRs when decided.

Accepted risk (see RISK_REGISTER R9 and R3): six new tools is a lot for a junior operator.
Each tool half-learned is an interview liability rather than an asset. The mitigation is
depth over breadth — learn each well enough to defend the choice and explain the
alternative — plus building a trivial end-to-end skeleton early so the ops path exists
before the model is good.

## Decision

| Slot | Chosen | One-line reason |
|---|---|---|
| Experiment tracking | MLflow, local backend | Self-hosted, free indefinitely, no external account; the recognised open-source tracker. |
| Data versioning | DVC | The standard data-versioning answer; git-like model transfers to interviews. |
| Data validation | Pandera | Lightweight, pandas-native, low ceremony; readable schema-as-code. |
| Orchestration | Prefect | Lighter than Airflow on a laptop; enough to show real DAG orchestration. |
| Prediction store | Postgres | Mirrors a production prediction store; runs in Compose. |
| Serving | FastAPI | Effectively settled by the project brief; pydantic gives schema validation for free. |

All versions pinned at install and recorded in the environment lockfile. Every library API
is treated as [VERIFY] against the pinned version's own docs before use, because MLflow,
DVC, Pandera and Prefect have all had breaking changes across major versions.
[TREND — recency-sensitive]

## Alternatives considered and rejected

- Experiment tracking: **Weights & Biases free tier** rejected — external dependency, and
  free-tier terms change; local MLflow keeps everything self-contained and costs nothing.
- Data versioning: **hash-and-manifest in git** rejected — sufficient for one immutable
  file and ~30 minutes of work, but a weaker portfolio signal than DVC.
- Data validation: **Great Expectations** rejected — heavyweight with a history of breaking
  major-version changes; **hand-rolled checks** rejected — fine functionally but weaker as
  a demonstrated skill.
- Orchestration: **Airflow** rejected — enterprise-standard but heavy to run on a laptop
  for this scale; **Makefile + scripts** rejected — honest but reads as under-built for an
  MLOps portfolio.
- Prediction store: **SQLite** rejected — one fewer container, but less representative of a
  production store than Postgres.

## Consequences

Positive:
- CV-legible breadth across the standard MLOps toolchain.
- Each slot has a written, defensible rationale ready for interview.

Negative / to manage:
- Learning-curve load is real; risk of shallow familiarity across six tools (R3, R9).
- More moving parts in Docker Compose to keep reproducible (R8, R10).

Open, tracked for future ADRs:
- Drift monitoring: Evidently vs NannyML vs custom statistical tests. Decide by P10.
  Custom tests would show deeper understanding; Evidently is faster and generates reports.
- Deploy target: undecided. Decide by P8. Does not block P1-P7.

## Review

Revisit at the P5 retro (first heavy use of MLflow + DVC + Prefect together). If any tool
is proving to cost more than it demonstrates, supersede this ADR rather than silently
dropping the tool.
