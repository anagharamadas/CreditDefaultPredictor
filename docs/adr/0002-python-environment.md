# ADR-0002: Python environment management — conda host, uv-locked dependencies

Status: ACCEPTED
Date: 2026-08-18
Phase: P0
Supersedes: none
Superseded by: none

ADRs are immutable once accepted. To change a decision, write a new ADR that supersedes
this one; do not edit this file.

---

## Context

P0 pinned the dependency set with uv (`pyproject.toml` + `uv.lock`, Python 3.12), and uv
created its own `.venv/` in the repo. Separately, a conda environment named
`credit-default-predictor` was created for this project on the same machine — conda is the
operator's existing habit for per-project isolation and is already the interpreter source
on this machine (`/opt/anaconda3`).

That left two environments claiming to be "the" project environment: an empty conda env and
a fully-synced `.venv/` (689 MB). Two candidate environments is a reproducibility hazard —
it is exactly the class of ambiguity ("which python ran this?") that this project exists to
demonstrate it can avoid. One had to win, and the choice had to be written down.

The forces:

- `uv.lock` is the pinning mechanism the project already committed to. Reproducibility of
  training runs and of the serving image depends on it, and it is the stronger portfolio
  signal than a `pip freeze` or a hand-maintained `environment.yml`.
- Nothing in the dependency set needs conda's non-Python package management (no MKL-linked
  builds, no CUDA, no system libraries outside wheels). Conda's value here is only that it
  supplies and isolates the interpreter.
- Whichever is chosen must be reconstructible from the repo by a stranger, not just
  reproducible in this shell.

## Decision

**The conda env is the project environment. uv is the dependency manager and `uv.lock`
remains the single source of truth for versions.**

Concretely:

- Conda supplies the interpreter only: `conda create -n credit-default-predictor python=3.12`.
- `uv` is installed *into* that env, so activating the env puts the right `uv` on PATH.
- `UV_PROJECT_ENVIRONMENT=$CONDA_PREFIX` makes uv install into the conda env rather than
  creating `.venv/`. It is exported automatically by a conda `activate.d` hook, and unset by
  the matching `deactivate.d` hook.
- Dependencies are installed with `uv sync --frozen --inexact`.
  - `--frozen` — resolve nothing; install exactly what `uv.lock` says.
  - `--inexact` — leave packages uv does not manage (conda's own `setuptools`, `wheel`,
    `packaging`, `pip`, and `uv` itself) in place instead of pruning them, which would
    otherwise desynchronise conda's package metadata from the env's actual contents.
- `.venv/` is deleted and is not recreated. It stays in `.gitignore` as a guard.
- The whole sequence is scripted in `scripts/bootstrap_env.sh`, which is idempotent and is
  the documented setup path in the README.

Verification that the environment matches the lock: `uv lock --check` (lock agrees with
`pyproject.toml`) plus `uv sync --frozen --inexact` being a no-op.

## Alternatives considered and rejected

- **Keep uv's `.venv/`; conda env used only to put `uv` on PATH.** Works, and is the least
  change. Rejected because the conda env would then serve almost no purpose while still
  existing — two environments, one of them decorative, which is the ambiguity this ADR is
  meant to remove. Also leaves 689 MB duplicated.
- **Conda-native: `conda install` / `pip install` into the env, abandon `uv.lock`.** Simplest
  mental model and the most conventional data-science setup. Rejected because it discards a
  fully-resolved, hash-pinned lockfile in favour of either `environment.yml` (loose pins, no
  transitive lock) or `pip freeze` (platform-specific, no resolution metadata), weakening the
  reproducibility story that later phases — the serving image, the retraining runs, the
  drift replay — all depend on.
- **Drop conda entirely; uv-managed `.venv/` only, `uv python install` for the interpreter.**
  The purest uv setup and a defensible answer in its own right. Rejected as a matter of fit
  rather than merit: the operator works in conda across projects, and forcing a different
  activation habit for this one project invites the wrong interpreter being used by accident
  — the same failure mode, arrived at from the other direction.

## Consequences

Positive:
- Exactly one environment. `conda activate credit-default-predictor` is the only setup step
  after bootstrap, and `which python` has one answer.
- `uv.lock` stays authoritative, so ADR-0001's "all versions pinned in the environment
  lockfile" holds unchanged.
- Console scripts (`dvc`, `mlflow`, `prefect`, `pytest`, `ruff`, `uvicorn`) are on PATH
  directly on activation; `uv run` also works and targets the same env. No `uv run` prefix
  is required.

Negative / to manage:
- The activation hook lives inside the conda env, which is not in git. A fresh clone does not
  get it for free — this is why `scripts/bootstrap_env.sh` exists and why the README points
  at it rather than at a bare `uv sync`. If the hook is missing, `uv sync` silently recreates
  `.venv/` and the two-environment ambiguity returns.
- `--inexact` means uv will not prune stray packages. Anything installed ad hoc with `pip`
  will persist unnoticed and will not appear in `uv.lock`. Discipline: add dependencies with
  `uv add`, never bare `pip install`.
- The environment is now conda-shaped, but the Docker image built in a later phase will not
  be — it will install from `uv.lock` directly. Train/serve parity therefore rests on the
  lockfile, not on the environment, which is the intended arrangement but should be asserted
  by a test when the image exists (P8).
- The conda env's Python patch version (3.12.13) is not itself pinned by `uv.lock`, which
  constrains only `>=3.12,<3.13`. Acceptable at this granularity; the container pins exactly.

## Review

Revisit at P8, when the serving image is built and train/serve parity becomes testable
rather than asserted. If the conda layer is by then contributing nothing the container does
not, supersede this ADR and move to a uv-only environment.
